# IndiaFOSS project review — 7 September 2026

My recommendation is to make the next milestone a reliable conference day: find a session, choose a plan, meet someone, exchange contacts, and send messages that survive connectivity changes. Keep the federation and live-media ambitions, but make their expansion depend on demonstrated attendee outcomes.

I reviewed all 35 open issues across Companion (17) and Chat (18), the open PR inventories, relevant issue discussions, current GitHub main snapshots, architecture decisions, evidence records, CI results, and selected implementation paths. Neutrino has issues disabled; neutrino-iroh has no open issues. This is a product, architecture, and targeted code review, not an exhaustive audit of every upstream Element/Rust file or a fresh device certification.

Reviewed snapshots: Companion `a74146cccc4d46e6e10dc9466f05f8d7c88a87c6`; Chat `6cb3ed373d6676a75a3a121ae1eaf45fc811db5e`. The local checkouts are older, and Chat's index reports extensive staged deletions alongside untracked copies. I used isolated GitHub snapshots rather than modifying those worktrees. GitHub issues, PRs, and settings were not changed.

## What I understand your goals to be

You want an unofficial, FOSS conference companion that respects attendee control and remains useful without dependable internet. Native Android should feel native; the PWA gives other platforms access to the conference features. Meeting people and retaining those connections is central. Mesh messaging should eventually connect naturally with ordinary Matrix accounts and remote participants, while preserving end-to-end encryption.

The explicit decisions matter: separate Companion and Chat products, a native Compose Android companion, no plaintext portal bridge, and—per your comment on [#181](https://github.com/hanthor/indiafoss-companion/issues/181)—bring an existing Matrix account or receive a temporary Spindle account. I would preserve these decisions and reduce the number of unfinished experiences an attendee encounters simultaneously.

The strongest existing foundations are the canonical event bundle, local attendee storage, progressively refined ranking, reusable Matrix client, and the mesh evidence harness. The recorded shaped-network experiments actually found a join-storm correctness bug. That kind of testing deserves more attention than counting untested utility functions.

## Findings to address first

### 1. The identity ADR assumes a stronger verification mechanism than exists

**High priority before automatic routing or conversation merging.** [ADR 0006](https://github.com/hanthor/indiafoss-companion/blob/a74146cccc4d46e6e10dc9466f05f8d7c88a87c6/docs/adr/0006-one-person-two-transports.md) says #111 already signs an identity-binding statement with the Matrix account's device key and verifies it through `/keys/query`. Its routing and merging design relies on that claim.

The implementation in [mesh-link.ts](https://github.com/hanthor/indiafoss-companion/blob/a74146cccc4d46e6e10dc9466f05f8d7c88a87c6/packages/matrix/src/mesh-link.ts) instead fetches a public profile, reads `in.indiafoss.mesh`, and compares two strings. It returns `verified` when they match. It does not verify the claimed device signature. The contact-sharing documentation accurately describes this weaker profile check.

A profile match can be useful, but it trusts the homeserver's assertion. A signed contact card separately proves possession of the card key; it does not by itself prove control of every Matrix account named on the card. The proposal currently collapses these distinctions.

**Proposal:** distinguish “profile matches,” “card signature valid,” “confirmed in person,” and “Matrix identity verified.” Correct the ADR's description of current code. Before automatic routing, specify the binding's signer, trust anchor, account identifiers, validity/revocation rules, and behavior when offline. Add an adversarial acceptance case: a person must not gain automatic routing to their mesh identity merely by putting somebody else's MXID on a self-signed card. This is a design/implementation mismatch; I did not demonstrate an exploit in the currently shipped manual handoff flow.

### 2. The PWA can permanently miss updates during an open session

**High priority for the conference-day promise.** In [updates.svelte.ts](https://github.com/hanthor/indiafoss-companion/blob/a74146cccc4d46e6e10dc9466f05f8d7c88a87c6/apps/web/src/lib/updates.svelte.ts), `checked` becomes true before the first fetch and never resets. An initial offline failure prevents subsequent calls from checking again until the module reloads. A successful morning check also prevents later checks during the same app session. The layout has no reconnect refresh path that bypasses this latch.

I reproduced the failure with the actual update functions, mocked fetch/storage, and Node's TypeScript stripping: calling `checkForUpdates` twice after an offline rejection made only one fetch.

**Proposal:** separate “request in flight” from “last successful check.” Offer manual refresh and bounded checks on reconnect/foreground. Keep the last good bundle usable throughout. Acceptance: open offline, restore connectivity, publish a room/time change, and receive it without restarting or losing the plan.

### 3. A reinstated talk can remain cancelled after an update

**High priority; reproduced.** [diffBundles](https://github.com/hanthor/indiafoss-companion/blob/a74146cccc4d46e6e10dc9466f05f8d7c88a87c6/packages/schedule/src/index.ts) detects cancellation only in the false-to-true direction. If a cancelled talk is reinstated with otherwise unchanged fields, the diff is empty. The update code then records the new revision without saving the new bundle. The attendee retains a cancelled talk while the app records that revision as handled.

The same branch drops changes outside the notification diff, such as event metadata. “No banner needed” currently means “do not apply the data.”

**Proposal:** persist valid new data independently of whether changes deserve a notification. Explicitly detect reinstatement. Test reinstatement, metadata-only updates, and restart after application. The native [EventRepository](https://github.com/hanthor/indiafoss-companion/blob/a74146cccc4d46e6e10dc9466f05f8d7c88a87c6/apps/android/native/app/src/main/kotlin/org/indiafoss/companion/data/EventRepository.kt) also deserves an atomic-cache-write improvement: its direct `writeText` can truncate the latest cached schedule on interruption and leave only the bundled fallback. That last risk is code-inspected, not crash-reproduced here.

### 4. “Fixed in Rust” and “available on a phone” are different states

The [media passthrough fix](https://github.com/hanthor/neutrino/pull/11) merged on 7 September. Chat main still pins `0.8.2-e2ee.4a9972d`, an earlier revision. The durability fix has reached that pin; the later media fix has not. The handoff's blanket “not pushed yet” statement is now stale, and the readable mesh identity has also reached Chat main.

**Proposal:** make a release manifest identify the exact Neutrino commit, iroh commit, AAR checksum, Chat commit, APK version/signing identity, and device evidence. A fix is complete for attendees when an installable APK contains it and its acceptance scenario passes. After updating media bindings, separately test the upload cap and thumbnail behavior; passthrough alone does not establish support for normal camera photos.

### 5. Chat's test pipeline currently supplies no test result

The [latest Chat test run](https://github.com/hanthor/indiafoss-chat-android/actions/runs/34097919438) fails at **Checkout with LFS**, before Gradle or tests. Code Quality Checks passed, but that does not substitute for running the tests. The underlying LFS error was not established from the available failed-step output.

**Proposal:** restore checkout and the test job before expanding the coverage backlog. Confirm that a clean build can retrieve the exact assets it needs. Do not disable LFS without checking which tests require its files.

There is a separate red [Companion Neutrino workflow](https://github.com/hanthor/indiafoss-companion/actions/runs/34091879430). Its failing contract job is the scheduled **stock-upstream** probe; the fork's iroh E2EE and flaky-link/crash jobs passed. It would be incorrect to report that run as proof that the shipping fork's encryption is broken. Give upstream capability probes and release gates distinct names/status reporting.

### 6. “Seamless fallback” needs recipient-specific delivery semantics

ADR 0006 defines mesh reachability using a live peer/gateway and classic reachability using a responding homeserver. Neither establishes that a particular recipient can receive and decrypt a message. A discovered peer is weaker evidence still. Automatic retry through a second account also risks duplicate messages if the first transport delivered but its acknowledgement was lost.

**Proposal:** ship account coexistence and explicit “Continue using this account” before automatic per-message fallback. Define queued, accepted locally, delivered, and read separately. Define cancellation and duplicate suppression across the two conversations before enabling auto-fallback. Preserve per-account trust and provenance.

The current [DM guard](https://github.com/hanthor/indiafoss-chat-android/blob/6cb3ed373d6676a75a3a121ae1eaf45fc811db5e/libraries/matrix/api/src/main/kotlin/io/element/android/libraries/matrix/api/room/StartDM.kt) is a useful stopgap, but its exception advises trying again when online. Its predicate depends on identity shapes, not connectivity; going online alone cannot make it pass. Give the user an actionable account-switch explanation, and verify the actual rendered error surface.

## Product direction I would choose

**Make contact exchange the connecting experience.** “We met, I saved your card, I can contact you later” links the conference and chat products naturally. Finish add-by-QR, clear discovery controls, and account-aware handoff before a merged timeline. A short mesh code should remain a recognition aid, as ADR 0008 correctly specifies.

**Keep ranking optional and short.** The current flow still describes reviewing every talk before resolving overlaps. Let someone bookmark three talks and immediately get a useful plan, then refine only decisions that affect their next few hours. Explain why a talk was selected and expose conflicting must-attend choices. Measure time to a useful plan through observed usability sessions; no tracking service is necessary.

**Reduce duplicated surfaces.** Chat still contains `ConferenceActivity`, a WebView of the Companion. It has its own storage/session context and URL handling; current `matrix:` primary links are not explicitly dispatched by that handler. This undermines the otherwise clear app split. Prefer opening the installed native Companion, with the PWA as fallback. If the WebView remains, give it explicit ownership and test every supported handoff offline. Do not build another full native conference UI inside Chat merely because its older roadmap still asks for one.

**Treat the real event bundle as release-critical.** Both current clients default to the 2025 fixture. Keep demonstrations visibly labelled and require a validated 2026 bundle, room mapping, room seeding, and consistent event identifiers before a conference release. Respect the existing decision to highlight destinations on the map; do not revive complex indoor navigation without evidence attendees need it.

**Keep the live-media experiment, but narrow its next proof.** Voice messages first, then a two-phone duplex voice call with measured latency, loss, interruptions, battery impact, and simultaneous text delivery. The [Opus PR](https://github.com/hanthor/neutrino-iroh/pull/12) is valuable codec/transport evidence, not yet a handset call demonstration. Video and a new iOS mesh client should follow convincing device evidence.

**Give temporary accounts an explicit end-of-event contract.** Your default-account decision is already made. What remains is credential recovery, expiry, export, conversion to a lasting identity, and what happens to contacts when the account expires. An archive stored only on an expiring account cannot be presented as durable backup. I would defer automatic history archiving until that lifecycle is settled.

## A concrete next milestone

I would call it **“Two people can rely on this for a conference day.”**

1. Correct the identity ADR and UI terminology; fix schedule refresh/reinstatement; restore Chat's test pipeline.
2. Build the media fix into a checksum-pinned APK and verify text, voice messages, and normal camera-photo behavior on two physical phones.
3. Complete QR contact exchange and discovery choice. Test Companion → Chat handoff without internet and with no chat handler installed.
4. Run screen-off/background, radio transition, force-stop/restart, and upgrade scenarios. Record delivery and decryption outcomes, duplicate counts, recovery times, and battery observations against exact APK versions.
5. Rehearse canonical room seeding and a joining burst on the real venue network. Distinguish shaped-software scale results from physical BLE/Wi-Fi capacity.
6. Publish a clear compatibility/readiness table: schedule available offline, installed mesh version, supported media, public-room availability, and unsupported cross-seam encryption. Keep transport diagnostics in a troubleshooting view; normal screens should explain what the attendee can do next.

Only then expand automatic account routing, merged conversations, and live calling. This sequencing preserves the larger ambition while producing something worth installing and trusting at each step.
